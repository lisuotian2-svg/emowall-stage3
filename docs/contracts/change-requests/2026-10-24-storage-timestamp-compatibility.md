## 为什么阶段性决定尚不足以证明完整契约一致

冻结 v1.2 只写 ISO-8601 UTC，没有将输入限定为扩展式 Z/+00:00。当前 CTE 对一些合法表示产生 NULL 排序键，并将它们与非法时间文本一起置尾；报告这些缺口不等于已经修复运行时行为，也不能把这些值改称非法来关闭问题。

## 数据调查与解析实测

本机项目内非临时位置未发现 .db 文件；按配置路径规则检查的用户数据目录及 emowall.db 均不存在。没有创建目录、打开或改写真实用户库。因此目前只能对构造历史数据库和固定样例给出证据，不能宣称所有历史数据都不含其他表示。

本机 Python 3.12.15、SQLite 3.53.1，隔离内存库实测：

| 表示 | Python fromisoformat | SQLite 日期解析 | 当前 CTE 排序/同刻行为 |
|---|---|---|---|
| 扩展式秒/毫秒/微秒 Z | 解析 | 解析；%f 仅毫秒，未用于实际小数排序 | 已通过 |
| 扩展式 +00:00 | 解析 | 解析 | 已通过，并与 Z 同刻并列 |
| 超过六位小数 | 解析但只保留六位 | 接受文本，日期函数不保留原小数精度 | CTE 保留原始小数字符，九位相邻值已验证；不应改用截断解析结果 |
| 基本式 `20261024T120000.123200Z` | 解析 | 不解析 | NULL 键，可能错排；已有反例 |
| 逗号小数 `2026-10-24T12:00:00,123200Z` | 解析 | 不解析 | NULL 键，可能错排；已有反例 |
| 零偏移 +0000 | 解析 | 不解析 | NULL 键，可能错排；已有反例 |
| 周日期 `2026-W43-6T12:00:00.123200Z` | 解析 | 不解析 | NULL 键，可能错排；已有反例 |
| 序数日期 `2026-297T12:00:00.123456Z` | 不解析 | 不解析 | 当前未支持；不据解析失败判断其违反 ISO |

前四个具体错排样例均比 `2026-10-24T12:00:00.123100Z` 新，当前却排在其后。24:00 需要明确与次日零点等价，不能仅因为 SQLite 接受就认定排序正确。

## 请求裁决

请明确以下范围与行为，不以修改历史数据或缩小契约为默认解决办法：

## 推荐与影响

推荐保留 CTE 已验证的精确小数比较，不恢复 HYBRID，也不使用 julianday 或六位截断。对决定纳入范围的表示，先增加真实运行失败测试，再只对查询时的解析/排序键扩展；保留原始文本、稳定 rowid 次序与 LIMIT 语义。

如需处理尚未支持的表示，优先在私有实现中精确解析，避免增加公共类型或修改 Schema；但标准库解析本身不能覆盖全部表中形式，也不能完整保留超过六位的小数，不能直接用 fromisoformat 作为全部合法表示的判定器。
