## 1. 相对于 v1.2 的正式调整

v1.2 将时间戳字段描述为“ISO-8601 UTC”，但没有枚举 `list_recent()` 必须能排序的文本形式，也没有约定遇到无法比较值时的公共结果。v1.3 拟将**该方法的读取保证**明确限定为下列完整 UTC profile，并把未支持或无法解析的 `updated_at` 变成显式错误。这是对 v1.2 宽泛表述的版本化调整，不能解释为旧实现已满足新保证。

| 项目 | v1.3 拟定公共保证 |
|---|---|
| 新写入时间戳 | `YYYY-MM-DDTHH:MM:SS.ffffffZ`，包含秒、恰好六位微秒；当前生成逻辑不变 |
| 历史读取格式 | 本文 §2 的完整文本 profile；既有秒/毫秒/微秒 `Z`、`+00:00` 与超过六位有效秒小数不得退化 |
| `list_recent(limit)` | 对同一候选快照的**所有**会话 `updated_at` 验证和精确比较，之后按真实 UTC 时间倒序、同刻 `rowid DESC`，最后应用 `limit` |
| 不可比较记录 | 抛 `StorageTimestampError`，**整次调用无列表结果**；不能置尾、跳过、返回部分结果或将错误列表当作成功 |
| 数据保持 | 返回原始时间戳字符串；不迁移、不自动规范化/修复历史行，Schema 仍为 1 |

本 profile 是工程上承诺支持的**有限读取集合**，不声称等于 ISO-8601 的全部合法表示。profile 外的文本不得一概宣称“不合法 ISO”；它们在 `list_recent()` 中仍须显式失败。

## 2. 必须支持的读取文本

下列语法从第一个字符到最后一个字符完整匹配。大写 `T`、`W`、`Z` 是字面字符；数字仅允许 ASCII `0`–`9`。`YEAR` 恰为四位、数值 0001–9999；`MM`、`DD`、`ww`、`HH`、`mm`、`ss` 均为两位，`D` 为一位，`DDD` 为三位。

```text
CAL_EXT    := YEAR "-" MM "-" DD
CAL_BASIC  := YEAR MM DD
WEEK_EXT   := YEAR "-W" ww "-" D
WEEK_BASIC := YEAR "W" ww D
ORD_EXT    := YEAR "-" DDD
ORD_BASIC  := YEAR DDD
TIME_EXT   := HH ":" mm ":" ss
TIME_BASIC := HH mm ss
FRACTION   := ("." | ",") ASCII_DIGIT+      # 可选，仅表示秒的小数
UTC_SUFFIX := "Z" | "+00:00" | "+0000" | "+00"

STAMP := (CAL_EXT | WEEK_EXT | ORD_EXT) "T" TIME_EXT FRACTION? UTC_SUFFIX
       | (CAL_BASIC | WEEK_BASIC | ORD_BASIC) "T" TIME_BASIC FRACTION? UTC_SUFFIX
```

日期与时间必须同为扩展式或同为基本式；四种零偏移后缀独立于日期/时间风格，基本式也可用 `+00:00`，扩展式也可用 `+0000`。不自动去空白、折叠大小写或接受额外尾字符。

- 公历日期必须有效。周日期的 `YEAR` 是周所属年，周号 01–53、周日 1–7 必须对该年有效；序数日 001–365/366 必须在该年。转换后的公历日期仍须落在 0001–9999 年。
- 常规时间 `HH` 为 00–23，`mm` 和 `ss` 为 00–59。`FRACTION` 至少一位且只含 ASCII 数字；任意有限位的有效数字参与比较，不截断到毫秒或六位微秒。
- `HH=24` 仅在分、秒及所有小数位为零时接受；比较时等于次日 00:00:00。跨出 9999 年必须报错，不能回绕。`24:00:00.0000000000000000001` 不可被截断后接受。
- `ss=60` 可能涉及闰秒，本 profile 暂不支持；不得笼统宣称所有这类文本在完整 ISO 范围内非法。已知合法闰秒文本同样须显式失败。
- 非零或未知偏移、扩展/负年份、约简日期或时间、小时/分钟小数、混合日期时间风格、小写或不完整文本，以及任何未列举表示，均不在当前读取保证内。匹配已支持形状但日期/字段无效的，诊断为无效；其余保守诊断为“不支持或无法识别”。

例如 `20261024T120000,123200+0000`、`2026-W43-6T12:00:00.123200Z`、`2026-297T12:00:00.123200Z` 均在范围内；`2016-12-31T23:59:60Z` 暂不在范围内。接受某个文本是本项目的兼容承诺，不单独声称它符合任何 ISO 版本的全部规范。

## 3. 比较、稳定次序和查询边界

支持的表示先换算为同一公历日、当天秒数及**不丢失有效位**的小数秒比较键。四种零偏移后缀等价；`.123` 与 `,123000` 等价；无小数与全零小数等价。不同文本代表同一真实时刻时，以 `rowid DESC` 打破平局。返回对象保留数据库中的原始 `created_at` 和 `updated_at` 字符串。

`list_recent(limit: int = 50) -> list[Conversation]` 的签名、默认值与 `limit` 必须为正整数的校验不变。对参数合法的一次调用，候选集合是同一数据库读取快照里的**全部 conversations 行**；每行的 `updated_at` 均须可比较。验证和排序完成后才应用 `limit`。即使坏记录显然不会进入前 `limit` 条，仍不能绕过验证。空表返回 `[]`。任一记录无法比较时，不得返回列表或修改数据库。失败后须释放本次查询资源，使同一有效连接仍可用于 `get(id)` / `list_messages(id)`；不得关闭连接或提交/回滚调用方已有事务。

SQL 可用于取得一致候选快照；时间戳识别与精确排序应依据本文规则实现，不能继续靠叠加 SQLite 日期函数和分支来猜测完整 ISO 语义。查询性能与内存占用须在实施验收时实测；性能不足时应报告并提出新方案，不得悄悄恢复错误排序。

## 4. 新公共异常及边界

```text
StorageError
└── StorageTimestampError
```

`StorageTimestampError` 定义于 `emowall.storage.errors`，并加入 `emowall.storage` 包级导出及 `__all__`；这是 v1.3 的第九个包级导出。现有 `StorageError` 捕获者仍可统一处理存储层错误。原三个子类的继承和用途不变。

仅当 `list_recent()` 已取得候选、但至少一个 `conversations.updated_at` 不在 §2 范围内或虽匹配形状却无法有效换算/比较时，抛此异常。异常提供**只读公共属性** `conversation_ids: tuple[str, ...]`：包含该次快照内所有无法比较会话的 ID，去重、按 ID 字符串升序，不能为空。该属性让调用方在列表失败后仍可准确定位每条受影响记录；错误消息只需说明原因类别和数量，不应被调用方解析以取得 ID。

异常消息、日志及诊断不得含会话标题、消息正文或整条原始时间戳；日志默认不打印 `conversation_ids`。对已支持形状中的无效日历值，可说明“无效”；对 profile 外文本仅说明“不支持或无法识别”，不把它判成非法 ISO。有真实底层解析异常时保留 `__cause__`；仅由本契约判定不支持/无效而无底层异常时不伪造 SQLite cause。多个坏值可按 ID 顺序关联第一个真实底层 cause，其他 ID 仍全列于属性中。这一新增逻辑错误明确补充 v1.2 §5.2.4 的异常链规则：该条继续要求**实际发生的**底层 SQLite/文件系统异常保留原 cause；无底层异常的格式判定不得制造 cause。

合法 `limit` 校验失败仍是 `ValueError`；SQL/文件 I/O 失败仍按原映射抛 `StorageIOError` 并保留真实 cause；关闭或跨线程使用等编程错误仍直接传播。`StorageTimestampError` 不能用于掩盖这些错误。`get(id)`、`list_messages(id)` 不增加时间戳 profile 验证，继续允许按 ID 读取原始历史数据；本次只验证 `list_recent()` 排序所用的 `updated_at`，不扩展到 `created_at` 或消息时间戳。

## 5. 列表不可用时的恢复路径与产品风险

**单条异常 `updated_at` 足以让整个正常会话列表不可用。** 这是避免静默错排的有意公共行为，不能仅以抛异常当作完整恢复方案。

1. `StorageTimestampError.conversation_ids` 给出全部受影响 ID。调用方可在原数据库工作线程内逐个用既有 `get(id)` 查看原始会话及 `updated_at`，用 `list_messages(id)` 读取消息；这两条读取路径不依赖 `list_recent()`，不因该列表错误被封锁。正常列表调用仍返回错误，不能改用未经排序的结果冒充“最近会话”。
2. 在修复前先制作并验证**一致的数据库备份**，保留原始值和消息。可对受影响记录做只读导出；不得在正常读取时自动删除、隔离、改写或选一个猜测时间。备份与导出不得依赖成功调用 `list_recent()`。
3. 只有能够从可信来源确认真实 UTC 时刻、用户明确同意并已有可恢复备份，才可在单独授权的修复流程中对指定 ID 事务性改写 `updated_at`；失败回滚，修复后重新运行 `list_recent()` 验证全表。若真实时刻无法确定，保留原文和可读取/可导出的历史数据，等待扩展读取 profile 或人工决定，列表仍明确不可用。
4. Stage 5 的数据库工作线程应专门捕获此 `StorageError` 子类，向界面显示“会话列表无法安全排序”、受影响条数及恢复入口；查看受影响 ID、原始时间和只读导出需由用户主动进入诊断/恢复视图。不得把异常当作网络故障、空列表或成功的部分列表。该界面与备份/修复工具属于后续 Stage 5 或另行授权工作，不能在本轮契约草案里冒称已实现。

即使受影响记录时间很早、`limit=1` 或仅有一条坏值，上述流程也一样。它保留用户数据访问能力，但在修复或扩展读取支持前**不能恢复正常最近列表可用性**；这是负责人须明确接受的可用性代价。
